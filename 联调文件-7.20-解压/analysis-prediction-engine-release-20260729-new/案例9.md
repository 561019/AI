案例九：数据分析与预测——李志刚问“六月前十名经销商本季度复购率为何环比降两个点”，平台先复核事实再倒推、定位到两家经销商、往下关联到那段时间配送延误集中与回访没跟上；他又要预测下季度桂中需求，平台给出预测区间与依据、关键数字“7月预订单比6月增20%”交付盛贤确认、不替谁拍板

李志刚在工作台问一句：为什么六月前十名经销商本季度复购率环比降了两个点？平台不急着给个说法，而是先把“降两个点”这个事实用确定性算法复核准，再一层层倒推找根因——先把降幅拆到每家经销商，定位到主要是两家在拉低，再往下把这两家那段时间的工作汇报关联进来，找出共同的问题：配送延误集中、回访没跟上。接着李志刚说：按现在的走势，预测下季度桂中的需求。平台调用现成的需求预测能力，给出一个预测区间、并指明依据（其中用到付盛贤5月8日的工作汇报）；预测里有个关键数字——7月预订单比6月增加20%——平台不把它当定论，标注为待付盛贤（一线最了解实况的人）确认，确认前不作准、更不替谁拍板。本场景是被动按需：李志刚问了才分析、问了才预测，平台提供分析与预测的能力，关键数字交真人把关。以下按调用链逐步说明，特别把每一步“调哪个引擎、判哪类权、数据怎么取”讲清（总体走法同案例一，不再重复）。

第一段：李志刚问复购率为何下降、平台复核事实再倒推找根因（人问才答·诊断）。

第一步　业务应用层组装请求、向下发往业务引擎层。李志刚在对话框问：为什么六月前十名经销商本季度复购率环比降了两个点。工作台把这句话组装为一条标准请求，含请求人（李志刚）、来源对话框、请求类别（自然语言）、原始表述，以及新建的追踪编号与本 Project 标识，经业务应用层接口向下发往业务引擎层；请求不随附整包对话记忆。

第二步　业务引擎层接口分流（第一处进层关卡判权）。业务引擎层接口控制模块接收，核对来源在准入名单、格式无误，按李志刚本人实时判权、留痕（进层关卡判权），再按类别分流：自然语言，交意图分析引擎。

第三步　意图分析引擎解析、取横向上下文、对到能力标识、意图确认（本段唯一一次）。意图分析引擎调大模型把请求解析为一件诊断的事：先复核六月前十名经销商本季度复购率环比降幅是否为两个点这一事实，再倒推这个下降的根因在哪。解析时本引擎需要围绕“这十名经销商”的既有背景，于是向下取横向上下文——经业务引擎层对内通道下达、由基础模块层记忆管理（1.15）按经销商维度把跨账号、跨事件长期积累的记忆读回（读这条记忆同样按李志刚本人实时判权）。随后把这件事对到能力字典中相应能力标识，将解析结果整体返回李志刚确认与其意图一致后交流程执行引擎。此为诊断与查看、非关键动作，本段仅此一次意图确认。

第四步　流程执行引擎对号入座、排先后（讲清这段调哪几个引擎）。流程执行引擎到唯一的能力登记表对号入座、确定性查表，定下这段要调的引擎与先后：取经销商复购的原始业务数据、做计数分组排序，用数据操作引擎；把复购率、环比降幅这类比率算出来、复核“降两个点”属实，用规则计算引擎；把降幅倒推到具体经销商、再关联工作汇报找共同根因，用分析预测引擎（且优先照知识地图调现成的根因分析能力）。按数据依赖排先后——先取数算率复核事实、再把降幅拆到经销商级定位到两家、最后关联这两家的工作汇报找共因。此步是确定性查表选引擎、不作语义比对、不调大模型。

第五步　取经销商复购数据、复核“降两个点”（数据操作取数＋规则计算算率）。流程执行引擎先派数据操作引擎取数：数据操作引擎按“六月前十名经销商”这个范围、圈定本季度与上一季度的复购相关业务数据（各经销商的下单、复购记录），发限定取数指令、经业务引擎层对内通道下达到基础模块层数据模块（1.7）；数据模块按其存储登记（记这些数据物理存于哪个库、哪个位置）到相应库把记录读回。读回这一刻，基础模块层层接口按李志刚本人对这批数据实时判取数权限（取数判权，判权归权限管理、数据模块只管取）。复购次数、订单数的计数与按经销商分组由数据操作引擎当场确定性算出；复购率（复购客户数占比）、本季度对上季度的环比降幅这类比率，交规则计算引擎按总量确定性算出、不由大模型心算——由此复核出“前十名整体复购率环比降两个点”确为事实。

第六步　倒推第一层：把降幅拆到每家、定位到两家（数据操作分组排序＋规则计算算各家降幅＋分析预测判主要贡献）。流程执行引擎续派：数据操作引擎按每家经销商分组、取各家本季度与上季度的复购数据（这批数据上一步已按十家取回、此处按家拆开，不足处再走同一条取数链补取、补取当口同样判取数权）；规则计算引擎逐家算出各自的复购率与环比降幅（比率、由规则计算引擎算），并按降幅大小排序；分析预测引擎据此判定这两个点的降幅主要由其中两家经销商拉低——“主要落在这两家”是归因判断、由分析预测引擎给出，排序与算率是前置的确定性步骤。至此把“整体降两个点”倒推到“主要是这两家”。

第七步　倒推第二层：关联这两家那段时间的工作汇报、找出共因（数据操作取工作汇报＋分析预测照知识地图调现成根因分析能力）。再往下找为什么是这两家。流程执行引擎派数据操作引擎按“这两家经销商”加“那段时间”两个标签，取该时段与这两家相关的工作汇报业务数据（即场景七里业务员随手报、写进工作日志的那类数据），发限定取数指令、经对内通道自数据模块（1.7）读回（读回当口判取数权）。找根因这件事要用现成的根因分析能力：由流程执行引擎先派知识地图引擎，照李志刚名下（及其有权共享调用）的知识地图挑出对得上“复购下降根因分析”的那一份现成技能或分身——挑哪一份的判断放在知识地图引擎内部做出；再派分析预测引擎，用选出的这份现成能力，从这两家的工作汇报里倒推出共同问题：那段时间对这两家配送延误集中、回访也没跟上。调用这份现成技能属调用资产、按李志刚本人实时判调用资产权。只有知识地图上确无对应现成能力时，才由大模型直接作答保障基本可用，并让李志刚反馈一次、据此把根因分析能力补出或添厚到地图上、越用越准。

第八步　诊断结论呈现李志刚（查看·无写入）。倒推的结论——复购率环比降两个点属实、主要由两家经销商拉低、根因是那段时间对这两家配送延误集中且回访没跟上，其中客观数字（复购率、降幅）由规则计算引擎确定性算出、归因由分析预测引擎倒推给出、供参考——为名称、数字、结论类硬信息，经业务应用层信息分发机制列于李志刚右侧（应请求才出现），中栏为分身的诊断话。此段全程诊断与查看、无写入、不涉及存改数与关键动作确认。

第二段：李志刚要预测下季度桂中需求、平台给预测区间与依据、关键数字交付盛贤确认（人问才答·预测＋关键数字真人确认）。

第九步　李志刚发问、进层判权、意图确认（本段唯一一次）。李志刚接着说：按现在的走势，预测下季度桂中的需求。这是新的一件事、另起一条请求，同样经业务应用层接口组装、向下；接口控制模块按李志刚本人实时判权、留痕（进层关卡判权），分流交意图分析引擎。意图分析引擎调大模型把它解析为一件预测的事：以当前走势为基础预测下季度桂中的需求；对到能力字典中相应能力标识，整体返回李志刚确认与其意图一致后交流程执行引擎。此为预测与查看、非关键动作，本段仅此一次意图确认。

第十步　流程执行引擎对号入座、排先后（讲清这段调哪几个引擎）。流程执行引擎到能力登记表对号入座、确定性查表，定下这段要调的引擎与先后：预测本身用分析预测引擎（且优先照知识地图调现成的需求预测能力）；预测要用的桂中历史需求与订单数据、以及作依据的付盛贤5月8日工作汇报，用数据操作引擎取（涉从公司现有系统取的走外部系统对接引擎）；预测里涉及的增长率、趋势比率这类比率用规则计算引擎确定性算。按数据依赖排先后——先选出预测能力、取齐历史数据与依据，再出预测区间。

第十一步　照知识地图选出现成需求预测能力（知识地图·技能/分身优先）。由流程执行引擎先派知识地图引擎，照李志刚名下（及其有权共享调用）的知识地图挑出对得上“区域需求预测”的那一份现成技能或分身——挑哪一份的判断放在知识地图引擎内部做出，可能是本人沉淀的预测技能、也可能是营销板块或某位经营专家共享出来的能力。调用这份现成能力属调用资产、按李志刚本人实时判调用资产权。只有确无这份现成能力时，才由大模型直接作答保障基本可用，并让李志刚反馈一次、据此把预测能力补出或添厚到地图上、下次照图就有现成的、越用越准。

第十二步　取桂中历史需求数据与作依据的工作汇报（数据操作／外部系统对接·判取数权）。流程执行引擎派数据操作引擎取预测要用的数据：按“桂中”标签取本区历史需求、历史订单等业务数据；作预测依据要用到付盛贤5月8日那条工作汇报的，按“付盛贤”加“5月8日”定位取那条工作汇报数据。均发限定取数指令、经对内通道下达数据模块（1.7）、由数据模块到物理库读回，读回这一刻按李志刚本人实时判取数权限（取数判权）。其中若历史订单等数据在公司现有系统里，由外部系统对接引擎经基础模块层设备与系统接口（1.10）通道取回、取回当口同样判取数权。

第十三步　分析预测引擎给出预测区间与依据（用选出的需求预测能力）。分析预测引擎用第十一步选出的这份需求预测能力，以取回的桂中历史需求、订单走势为输入，给出下季度桂中需求的一个预测区间——是一个区间、不是一个死数，并指明依据里用到了哪些东西（其中一条依据是付盛贤5月8日工作汇报里反映的一线情况）。预测里涉及的增长率、环比这类比率由规则计算引擎确定性算出、不由大模型自估。此为预测与研判、供参考，不改动任何数据。

第十四步　关键数字交付盛贤确认（关键数字·第三方真人确认）。预测里有一个关键数字——7月预订单比6月增加20%。这个数字带着一线实况的判断、又直接影响预测，平台不以算出或推出即当定论——按“关键数字须经真人确认”的既定做法，把它标注为“待付盛贤确认”，经流程执行引擎编排、由监控提醒引擎异步送达一线最了解实况的付盛贤。付盛贤在其界面（进入时判进层关卡权）按该追踪编号认领、核对这个20%到底准不准、确认后此数字方作准——此确认由权限管理判付盛贤本人对该数据的确认之权后生效、留痕。确认前，该数字在李志刚屏标为“待付盛贤确认”、不作准；这是第三方真人确认（付盛贤并非发问人李志刚）、经监控提醒引擎异步送达，与意图确认（只跟发问人本人、当场进行）分属两类，靠同一追踪编号认领。平台只把关键数字交真人把关、不替谁拍板。

第十五步　预测结论呈现李志刚、全程留痕各请求各编号。预测区间、预测所依据的东西、以及那个带“待付盛贤确认／已确认”状态的关键数字，均为名称、数字、状态类硬信息，经业务应用层信息分发机制列于李志刚右侧（应请求才出现），中栏为分身的预测话。第一问诊断那段、第二问预测那段、付盛贤确认关键数字那次，各以各自追踪编号贯穿、逐步留痕，可回溯这次分析取了哪些数、用了哪份现成能力、哪个数字是谁确认的。本场景被动按需——李志刚问了才分析、问了才预测；全程无写入、除付盛贤对关键数字的一次确认外无真人拍板。

本案例把数据分析与预测这个场景的引擎时序、数据存取、权限三条线一并走清。何时调哪个引擎：意图分析引擎只在每次发问时出一次场，把话解析成要办的事、需要时向下取记忆管理（1.15）里的横向上下文、并做那一次意图确认；流程执行引擎在每次解析后到能力登记表对号入座、确定性查表定下调哪几个引擎与先后（确定性查表这一步不调大模型）；数据操作引擎承担一切取数、计数、分组、排序（取经销商复购数据、按家拆分、取工作汇报、取桂中历史需求与作依据的工作汇报）；规则计算引擎承担一切比率与达标判定（复购率、环比降幅、各家降幅、预测里的增长率与趋势比率），复核客观事实、不由大模型心算；分析预测引擎承担倒推归因与需求预测两件分析活，且都优先照知识地图调现成的技能或分身、确无才由大模型直接作答保障；知识地图引擎只在要用现成技能时先被流程执行引擎派去选、挑哪一份的判断在其内部做出、办事引擎不自读图；监控提醒引擎负责把关键数字异步送达付盛贤请其确认。数据怎么存取：一切业务数据都走同一条取数链——引擎发限定取数指令→经对内通道→数据模块（1.7）按存储登记到物理库读回；凡从公司现有系统取的经外部系统对接引擎走设备与系统接口（1.10）；每一次读回、取回都在当口按操作真人实时判取数权、判权归权限管理、数据模块只管取不判权；横向上下文取自记忆管理（1.15）。权限触点：进层关卡判权（两次发问、付盛贤进屏确认）、每一次取数的取数判权、调用现成分析能力的调用资产判权、付盛贤确认关键数字经权限管理放行判权；全案无写入——诊断与预测都只是供参考、不改动任何业务数据，故无存改数判权、无关键动作确认。与前几案相比，本案落点在被动按需的分析与预测：会倒推找根因、会给预测区间，但客观数字由确定性算法算、关键数字交一线真人确认，平台只提供分析与预测的能力、不替人拍板。
