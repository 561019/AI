# L1.2 与 L2 整体设计方案（组织架构版）

版本：v0.1  
日期：2026-07-11  
依据文件：流程模板管理模块研发方案 v0.1、流程模板管理模块技术逻辑图 v1.0、流程执行引擎研发方案 v0.3、汉和 AI 平台四层架构图、岗位架构与权限授权机制说明、数据机制说明、数据运算与分析准确性机制说明。

## 一、总判断

当前需要把原先“流程管控”的能力拆成两层：

1. L1.2 只做固定流程模板管理，负责“固定流程应该怎么走”的模板资产。
2. L2 流程执行引擎负责“某一次流程实例实际怎么跑”，包括取模板、锁版本、拆任务、派发、暂停、审批、驳回、续跑、留痕。

这样拆分后，L1.2 不再是一个大而全的流程平台，也不再承担主控 Agent、LangGraph、Dify、Temporal 的运行职责。L1.2 是底层能力包；L2 是业务执行组织者；L4 是员工看到和操作的工作台或维护界面。

标准调用链为：

```text
L4 员工工作台 / 模板维护界面
  -> L2 业务引擎层 / 流程执行引擎
  -> L1 层接口控制模块
  -> L1.2 固定流程模板管理模块
```

L4 不直接调用 L1.2；其他 L1 模块也不直接读 L1.2 模板库。业务日常调用原则上都由 L2 统一封装，L1.2 只向 L2 提供确定性模板服务。

## 二、为什么必须这样拆

公司现在的组织不是传统“部门树 + 固定领导审批”的结构，而是岗位、真人、域、项目、上下级关系、授权规则共同决定权限。一个真人可以兼多个岗位，岗位和人会变化，权限来自制度和授权，不来自 AI。

因此模板不能写死“王敏审批”这种具体人，只能写：

- 哪个岗位负责；
- 什么条件进入哪个审批层级；
- 哪一步是自动节点；
- 哪一步是必须真人拍板；
- 驳回后退回哪里或结束；
- 适用公司、业务域、制度依据。

运行时由 L2 拿模板，再经组织权限能力解析“当前这个岗位此刻对应哪个真人”。这样人员变动不需要改模板，责任又能落到真实人。

## 三、L1.2 设计方案

### 3.1 模块定位

L1.2 名称：流程模板管理模块。  
一句话定义：L1.2 管“固定流程模板是什么”，不管“流程实例怎么跑”。

它是全平台固定流程模板库和版本治理能力包，面向 L2 提供模板登记、修改、发布、停用、取用、导入导出、审计、健康检查等服务。

### 3.2 目标

L1.2 的目标是把公司反复使用、步骤稳定、涉及资金或关键经营动作的流程固化成可治理的模板资产。

核心目标：

- 固定流程有统一模板来源，不散落在 Agent 提示词、个人经验或各业务系统里。
- 新建、修改都先进入草稿，不影响已发布版本。
- 真人确认后发布，生成递增版本号。
- 已发布版本不可覆盖，历史版本保留可查。
- 停用后不允许新发起流程，但历史版本仍可查询。
- 在途流程按发起时锁定的模板版本走完，不受改版影响。
- 模板中存岗位，不存具体人。
- 每一次维护、发布、停用、取用都可留痕。

### 3.3 任务

L1.2 负责以下任务：

- 固定流程模板草稿登记：`template.register_draft` / `template.create_draft`
- 固定流程模板草稿修改：`template.update_draft`
- 模板定义预检：`template.validate_definition`
- 真人确认后发布新版本：`template.publish`
- 停用和解除停用：`template.disable` / `template.enable`
- 取用已发布模板：`template.retrieve`
- 查询模板清单：`template.list`
- 查询办理留痕：`template.audit`
- 草稿与发布版差异：`template.diff_draft`
- 模板治理报告：`template.governance_report`
- 模板库健康检查：`template.catalog_health`
- 单模板导出与模板包导入：`template.export_template` / `template.import_bundle`
- 模板目录导出给 L2 联调：`template.export_catalog`
- 基于已有模板克隆草稿：`template.clone_template`
- 删除未发布草稿：`template.delete_unpublished`

### 3.4 边界

L1.2 不负责：

- 不做自然语言意图识别。
- 不判断员工一句话属于哪个业务流程。
- 不创建 Agent 或 Skill。
- 不拆分任务。
- 不生成执行计划。
- 不运行流程实例。
- 不推进节点。
- 不处理并行、条件分支、循环、暂停、续跑。
- 不发送通知、待办、企微消息。
- 不做真人审批决策。
- 不维护在途流程状态。
- 不做岗位找人。
- 不做真实权限判定。
- 不直接调用 OA、ERP、CRM、数据模块或其他 L1 模块。
- 不使用大模型，不做提示词，不做数字计算。
- 不接 Dify、LangGraph、Temporal。

这些能力分别归 L2 流程执行引擎、L1 接口控制、1.1 岗位权限、1.7 数据、1.10 系统接口、规则引擎、通知/工作台等模块处理。

### 3.5 模板结构

模板最少包含：

- `template_id`：固定模板编号。
- `name`：模板名称。
- `category`：模板类别。
- `owner_position`：模板责任岗位。
- `applicable_scope`：适用公司、业务域、是否固定流程。
- `version_policy`：新发起取最新发布版，在途实例保持原版本。
- `steps`：步骤列表。
- `rejection_policy`：驳回策略。
- `policy_file_refs`：制度文件引用。

步骤类型包括：

- `auto`：自动执行步，由 L2 派发给对应引擎或模块。
- `condition`：条件分流步，由 L2 或规则引擎按条件判断。
- `human_approval`：真人拍板步，模板只写审批岗位。

模板禁止写入具体人字段，例如 `approver_person_id`、`recipient_person_id`、`assignee_person_id`、`person_id`。

### 3.6 与组织权限结合

L1.2 遵守以下规则：

- 权限归岗位，责任归真人。
- 模板存岗位代码，不存人员姓名。
- 当前操作人必须通过 L1 接口控制和 1.1 权限校验。
- L1.2 不缓存组织架构，不保存权限副本。
- 岗位为空、多人同岗、临时代岗、自审批冲突等情况由运行时 L2 结合组织权限模块处理。

这适配当前“岗位 + 真人 + 域 + 项目 + 授权关系”的组织结构，而不是传统部门树。

## 四、L2 流程执行引擎设计方案

### 4.1 模块定位

L2 流程执行引擎是 L2 层唯一的流程执行组织者。  
一句话定义：L2 管“这一次流程实例怎么跑”。

它不保存固定模板本体，不替代 L1.2；它从 L1.2 取模板，锁定版本后运行实例。

### 4.2 目标

L2 的目标是把员工发起的事务变成可运行、可暂停、可追踪、可审计、可恢复的流程实例。

核心目标：

- 接收 L4 或意图分析后的流程请求。
- 判断固定流程或临时组装流程。
- 固定流程向 L1.2 取模板并锁定版本。
- 审批类、资金类、关键经营动作必须走固定流程模板。
- 临时组装流程只用于探索性、非关键动作。
- 按模板推进自动节点、条件节点、真人节点。
- 向其他 L2 引擎或 L1 能力派发子任务。
- 遇到真人拍板节点暂停，生成待办。
- 真人通过后继续，驳回后按模板驳回策略处理。
- 维护流程实例状态、节点状态、子任务状态、审计记录。

### 4.3 任务

L2 负责以下任务：

- `flow.start`：发起流程实例。
- `flow.get`：查询单个流程实例。
- `flow.list`：按发起人、状态、模板查询流程实例。
- `flow.decide_human`：处理真人拍板通过/驳回。
- `flow.dispatch_status`：接收子任务执行结果回报。
- `flow.audit`：查询流程实例审计记录。
- 固定模板维护入口转发：将 L4 模板维护界面发来的 `template.*` 请求经 L2 转给 L1.2。

### 4.4 固定流程与临时流程

固定流程：

- 适用于采购审核、报销审批、付款申请、提成计提、营销费用审批、用印、对外发布等反复使用且涉及责任的场景。
- 由 L1.2 保存模板，L2 发起实例时取模板。
- 发起人不能随意改审批链。
- 涉及资金和关键经营动作必须使用固定流程。

临时组装流程：

- 适用于一次性、多步骤、探索性、非关键动作。
- 由 L2 根据意图分析结果临时串联执行。
- 可以调用 Agent / Skill / 数据 / 知识库 / 沙箱等能力。
- 不得绕过资金、审批、对外承诺等固定流程要求。

### 4.5 L2 如何调用其他模块

L2 不要求 L1 模块之间互相调用，而是由 L2 作为业务执行组织者统一调度：

- 需要 Agent / Skill：调用 1.1 创建层或其登记能力。
- 需要模型：调用 1.5 大模型调度。
- 需要上下文：调用 1.6。
- 需要数据：调用 1.7 数据模块。
- 需要账号与权限：调用账号网关和 1.1 权限。
- 需要外部系统：调用 1.10 设备与系统接口。
- 需要知识库：调用 1.13。
- 需要沙箱执行：调用 1.14。
- 需要记忆：调用 1.15。

L1.2 在这个体系里只提供固定模板，不直接调这些模块。

## 五、L4 界面的责任

L4 是员工实际看到的界面，不属于 L1.2 本体，但需要按本模块接口设计。

L4 有两类入口：

1. 员工一句话发起流程：进入 L2，由意图分析和流程执行引擎处理。
2. 模板维护界面：用于业务部门和平台人员维护固定流程模板，操作仍经 L2 转交 L1.2。

L4 可以提供“新建草稿、修改草稿、预检、发布、停用、解除停用、导入、导出、查看版本、查看审计”的界面，但这些操作的真实状态来源必须是 L1.2 后端，不应只是前端模拟。

### 5.1 统一流程设计界面

固定流程和灵活流程可以共用同一个“流程设计/流程管控界面”，但底层职责必须分清。

用户在自身对话框用自然语言发起流程后，应用层进入流程管控界面。此时用户可以选择固定流程，也可以选择灵活流程；如果用户已经用自然语言描述了流程，L2 负责生成流程设计草稿并检查是否合理。检查不通过时，系统把问题告诉用户，用户可以要求 AI 修改流程草稿。

统一界面应包含：

- 自然语言流程描述。
- 流程类型：固定流程 / 灵活流程 / 自动判断。
- 流程草稿节点。
- 节点校验结果。
- 缺失岗位、缺失条件、缺失服务引用、关键业务风险提示。
- 用户确认与修改入口。
- 运行入口。
- “沉淀为固定流程模板”入口。

### 5.2 固定流程与灵活流程的共同点

两者在界面上都可以有：

- 草稿。
- 设计。
- 校验。
- 修改。
- 节点预览。
- 真人拍板/知会节点。
- 条件分支。
- 自动节点。

因此前端没有必要做成两个完全不同的系统。

### 5.3 固定流程与灵活流程的根本区别

固定流程：

- 属于制度化、反复使用、涉及责任的流程。
- 模板最终进入 L1.2。
- 发布必须真人确认。
- 有版本、停用、历史保留、在途锁版本。
- 发起人不能运行时随意改审批链。

灵活流程：

- 属于一次性、探索性、非关键动作流程。
- 设计草稿和运行归 L2。
- 可以由 AI 根据自然语言拆解和修改。
- 可以运行前校验。
- 不能绕过资金、合同、用印、对外发布、关键数字入账等固定流程要求。

### 5.4 灵活流程转固定流程

当某个灵活流程经常复用，或用户希望沉淀为公司固定做法时，L2 可以把流程设计草稿转换为固定模板草案：

```text
L4 统一流程设计界面
  -> L2 flow.design_from_text / flow.design_update / flow.design_validate
  -> 用户确认沉淀为固定流程
  -> L2 flow.design_convert_to_template
  -> L2 经 template.register_draft 转交 L1.2
  -> L1.2 保存为固定模板草稿
  -> 后续再由 template.publish 真人确认发布
```

这里 AI 可以帮助整理流程、检查合理性、生成模板草案，但 AI 不能直接发布固定模板。固定模板一旦进入 L1.2 并发布，就属于公司制度化流程资产，必须由真人确认。

## 六、数据与持久化设计

L1.2 的数据：

- 模板记录。
- 草稿定义。
- 已发布版本。
- 模板状态。
- 服务登记。
- 模板取用和维护审计。
- 制度文件引用。

生产环境建议：

- 结构化数据落 PostgreSQL。
- 制度文件、附件原件落平台统一文件存储。
- 模板定义只保存结构化规则和引用，不保存外部系统数据副本。

L2 的数据：

- 流程实例。
- 当前节点。
- 节点执行记录。
- 子任务派发记录。
- 人工待办。
- 通知记录。
- 审批决定。
- 驳回原因。
- 版本锁定信息。
- 全链路 trace。

Temporal 可在后续接入 L2，用于长时间暂停、断点续跑、故障恢复和更强的历史留痕；不属于 L1.2 必须引入的部分。

## 七、关键约束

1. 审批类流程一律走固定模板，不能由 AI 运行时临时编审批链。
2. 真人介入点必须在模板或执行计划中预先设定，AI 不能运行时自行增加或跳过关键拍板。
3. 模板写岗位，不写人。
4. 责任最终落到真实操作人、审批人、发布人。
5. 跨岗位、跨域、跨公司边界时，L2 必须触发权限校验。
6. 涉及计算的节点，AI 不自算，必须调用确定性工具或规则引擎。
7. 已发布模板不可覆盖，只能发新版本。
8. 停用不等于删除，历史版本保留。
9. 在途流程按发起时模板版本走完。
10. L1.2 不越权调用其他模块，L2 负责运行编排。

## 十一、2026-07-13 架构更新

### 11.1 固定模板 DSL 成为 L1.2 与 L2 的共同契约

固定模板和 L2 流程设计草稿使用同一组核心运行字段：节点标识与类型、服务/条件引用、`depends_on`、条件分支、重试/失败策略、真人节点超时策略及岗位型真人字段。L1.2 负责发布前静态校验，L2 在设计阶段实施同类 DAG 与分支校验。灵活流程沉淀为固定模板时必须完整保留这些字段，不能只复制节点名称和类型，否则会改变已确认流程的执行语义。

### 11.2 L2 运行保障职责明确

L2 本地运行底座已补充受约束状态迁移、子任务代次及回调防重防乱序、投递重试/退避/死信、流程取消、真人例外闭环和带单调序号的审计事件。这些属于 L2 的运行编排职责，不改变 L1.2 只管理固定模板资产的边界。

### 11.3 仍待生产化的责任边界

本地 JSON 仓库仅用于演示和测试。生产环境必须由平台批准的事务数据库实现跨进程并发控制、CAS/乐观锁、数据迁移、备份恢复和统一归档。真实岗位授权、代办、通知、承办引擎与外部系统仍通过各自模块和接口控制层接入；L2 仅消费其授权或执行结果。

### 11.4 L2 是平台任务运行中枢

L2 流程执行引擎不是仅服务审批或“流程类”需求的组件，而是平台中负责推进已确认用户任务的运行中枢。所有自然语言任务先由意图分析完成理解和确认；所有业务页面的结构化任务由 L2 接口接收；随后均由 L2 创建任务实例、决定固定模板或动态执行计划、派发承办引擎子任务、处理回调与真人介入、维护状态并送达结果。

固定模板审批只是任务运行中枢处理的一类高治理任务。内容草稿、文档解析、数据汇总、知识问答、数字资产创建、外部系统操作和多步骤经营任务同样必须在已确认或已结构化后进入 L2。意图分析不派发执行引擎；执行引擎群也不相互调用，只有 L2 流程执行引擎拥有任务推进和子任务派发权。
