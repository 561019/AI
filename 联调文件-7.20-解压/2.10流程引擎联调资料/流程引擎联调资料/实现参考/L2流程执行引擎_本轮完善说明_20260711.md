# L2 流程执行引擎本轮完善说明

日期：2026-07-11

## 本轮新增

0. 统一流程设计草稿能力：
   - `flow.design_from_text`：根据用户自然语言生成流程设计草稿。
   - `flow.design_get`：按草稿 ID 查询单个流程设计草稿。
   - `flow.design_list`：按发起人、状态、流程类型查询草稿列表。
   - `flow.design_update`：用户或 AI 修改流程草稿后更新。
   - `flow.design_validate`：检查流程是否合理。
   - `flow.design_convert_to_template`：将确认后的流程设计沉淀为 L1.2 固定模板草稿。

1. 固定流程发起时，L2 不只锁定 `template_id` 和 `version`，还会把模板运行摘要写入实例：
   - 模板状态、类别
   - 责任岗位
   - 适用范围
   - 版本策略
   - 驳回策略
   - 制度文件引用

2. 人工驳回支持按模板策略处理：
   - `end` / `terminate` / `fail`：驳回后结束。
   - `return_to_step`：退回指定节点重新执行。
   - `return_previous_step` / `return_to_previous_step` / `return_previous_step_or_end_by_template`：退回上一节点；没有上一节点则结束。

3. 每次驳回处理写入 `artifacts.rejection_history`，记录驳回节点、人工任务、处理动作、目标节点、原因和时间。

4. 本地组织壳子补充 `finance_owner`、`finance_template_owner`，用于财务类模板演示。生产环境仍应由 1.1 岗位权限模块解析。

5. 固定模板运行支持 L1.2 的 `human_notify` 节点。知会节点只记录通知类人工任务，不阻断流程；拍板节点才暂停等待决策。

6. 执行循环从“按列表顺序执行”升级为“按依赖调度”：
   - 节点支持 `depends_on`。
   - 固定模板如果未写 `depends_on`，默认按步骤顺序串行。
   - 固定模板如果显式写 `depends_on: []`，可作为并行起点。
   - 临时流程的多渠道分发示例已按依赖表达：先生成计划，再并行分发，最后汇总。

7. 自动节点支持基础异常处理：
   - `max_retries`：失败后最多重试次数。
   - `failure_policy`：超过重试后失败或升级真人例外待办。
   - 临时流程默认给自动节点 1 次重试机会，固定模板由模板定义决定。

8. 接口返回增加 `platform_status`，对齐方案中的五种平台状态：
   - `accepted` -> `已受理`
   - `in_progress` -> `办理中`
   - `waiting_human` -> `待真人确认`
   - `completed` -> `已完成`
   - `failed` -> `无法办理`

9. 条件节点支持分支路径控制：
   - 条件节点可在模板中声明 `branches`。
   - 规则承办引擎回传 `branch` 或 `condition_outcome`。
   - L2 按命中的分支标记未选路径节点为 `skipped`，后续汇总节点可依赖“完成或跳过”的分支节点继续推进。
   - 未配置的条件节点保持原有行为，不影响旧模板。

10. 灵活流程转固定模板时保留 `human_notify` 节点；知会节点必须携带 `notify_position`。

11. 流程设计草稿纳入本地状态仓库：JSON 演示仓库会随流程实例一同保存草稿，服务重启后可按 `design_id` 查询。生产环境应由平台 PostgreSQL 仓库替换该实现。

12. 真人拍板支持四种处理动作：
   - `approved`：通过并继续。
   - `rejected`：按模板驳回策略结束或退回。
   - `modified`：记录真人修改内容到 `human_modifications`，再继续后续节点。
   - `answered`：真人直接答复并结束本次流程，结果写入 `final_result`。

   修改内容和直接答复通过 `decision_payload` 传递。L2 负责留痕与状态推进；下游承办引擎如何使用修改内容，需在联调契约中明确。

13. 预设真人节点支持超时治理：
   - 模板步骤可配置 `timeout_seconds` 和 `timeout_policy`。
   - `flow.scan_timeouts` 供平台定时任务调用，扫描处于待真人确认的节点。
   - `timeout_policy=fail` 将流程置为无法办理；`timeout_policy=escalate_human` 创建例外真人待办。
   - AI 不得自行决定超时处置方式，处置策略必须写在模板中。

## 边界不变

L2 不保存固定模板本体，不替代 L1.2。模板定义、草稿、版本、停用、发布仍归 L1.2。

L2 负责流程设计草稿与流程实例运行：自然语言生成设计草稿、校验设计、转固定模板草案、取模板、锁版本、生成执行计划、推进节点、处理真人拍板、派发子任务、记录状态和审计。

固定流程和灵活流程可以共用一个 L4 设计界面，但底层归属不同：

- 灵活流程设计草稿归 L2。
- 固定模板草稿、发布版本、停用和历史版本归 L1.2。
- 灵活流程转固定流程时，L2 只能调用 L1.2 登记草稿，不能直接发布。

## 2026-07-13 运行底座更新

### 状态、取消与人工处理

- L2 将实例、节点、真人任务和子任务状态纳入受约束迁移，并在持久化前检查实例不变量。
- 新增 `flow.cancel`：取消非终态实例、关闭本地待办、记录取消证据；已经派发的外部子任务仅标记为需要下游取消，不伪称已停止外部执行。
- 取消后的迟到子任务回调会被忽略并留痕。
- 真人决策增加 `HumanDecisionAuthorizer` 端口；本地策略只允许当前承办人决策，生产可接入岗位授权、委托与代办结果。
- 自动节点升级的 `exception_review` 待办已可闭环：真人可重试最后失败节点、直接答复结束或确认终止。

### 可靠派发与通知投递

- 子任务 ID 包含派发代次，避免重试或驳回重跑时旧回调写入新一轮执行。
- `flow.dispatch_status` 支持 `callback_id` 去重及 `callback_sequence` 乱序防护。
- 工作台待办/知会投递记录包含状态、尝试次数、下次重试时间和死信终态。
- `flow.retry_workbench_delivery` 用于单条重试；`flow.scan_delivery_retries` 按退避时间扫描重试。

### 设计校验、查询与审计

- L2 设计草稿校验依赖关系、依赖环、条件分支目标和分支冲突，并在转 L1.2 模板时保留依赖、分支、重试和超时字段。
- `flow.list` 支持带上限的偏移分页；`flow.audit` 限制单次读取上限。
- `flow.health` 汇总实例状态、待办、失败子任务、待重试投递和死信数量。
- 审计事件新增单调 `sequence` 与稳定 `event_id`。

### 当前验证与边界

截至本次更新，L1.2 + L2 单元测试为 45 项通过，L1.2 验收为 64/64 通过。上述能力仍是本地可测试、可联调运行底座；跨进程事务存储、生产 outbox/inbox 调度、复杂补偿语义和真实模块联调不在本地演示实现范围内。

## 2026-07-15 平台协议适配

根据《平台层间通信与权限协议 v0.5》，L2 流程执行引擎新增独立的平台协议适配层，不改变既有运行内核的职责。

- 标准服务代码为 `l2.workflow_execution`。
- 适配层接收公共请求信封，校验协议版本、目标服务、动作、责任真人、执行/维护幂等键和截止时间。
- 支持 `flow.start`、`flow.get`/`task.get`、`flow.list`/`task.list`、`human.decide`、`flow.callback`、`flow.cancel`、健康检查及定时扫描动作。
- 回复统一转换为 `success`、`accepted`、`failed` 三种标准语义；未完成的流程发起返回 `task_receipt`。
- 演示服务新增 `/health`、`/api/v1/capabilities`、`/api/v1/instructions` 和 `/api/v1/callbacks`。既有 `/api/*` 路径仅作本地演示兼容，不是跨模块联调契约。

该适配层只做协议映射和输入边界校验。服务目录准入、权限决策、跨模块 HTTP 转发、统一审计和生产级幂等缓存仍由平台 L2 接口控制模块接管；流程执行引擎继续是唯一能推进流程状态和派发执行引擎子任务的业务内核。

适配层同时执行最小 L2 路由白名单：业务页面只能通过 `l4_to_l2` 发起 `business.submit`/`task.submit`；意图分析只能通过 `l2_internal` 发起 `flow.start`；承办引擎只能通过 `callback` 回传 `flow.callback`；真人决定只能通过 `l4_to_l2` 进入；超时与投递扫描只能通过 `scheduled` 信道进入。违反来源层级或信道约束时返回 `failed(caller_not_allowed)`。

## 2026-07-15 任务运行中枢定位

L2 流程执行引擎是平台的任务运行中枢，不限于审批或传统流程任务。它负责推进所有已经完成意图确认或由业务页面提交的结构化用户任务：创建任务实例、选择固定模板或动态计划、拆分节点、派发承办引擎、处理回调与真人介入、维护运行状态并将结果交回 L4。

- 自然语言任务：`L4 -> 意图分析 -> 已确认结构化命令 -> L2 流程执行`。
- 结构化业务任务：`L4 业务页面 -> L2 接口 -> business.submit/task.submit -> L2 流程执行`。
- 系统任务：已登记回调、待办决定和定时扫描通过标准信封进入 L2，不伪装为用户自然语言。

固定审批模板、内容生成、数据处理、知识问答、数字资产创建和外部系统操作在运行时均是 L2 任务实例的不同节点组合；具体能力仍由登记的承办引擎完成，L2 不吸收其领域算法或外部系统实现。

## 2026-07-20 能力登记选派与版本冻结

依据最新《架构组交付总索引》《数据流转、对接与通信交互规范》和 v2.2 决议，L2 的正式选派路径为：

```text
已确认结构化命令的 capability_ids
-> L2 查询能力登记表
-> capability_id 映射 service_code / action / schema_version
-> 冻结能力字典、登记表、服务和 Schema 版本
-> 创建 node 与 dispatch_task
-> 经 L2 对内通道派发
```

每个冻结记录至少包含 `capability_id`、`capability_dictionary_version`、`registry_version`、`service_code`、`action` 与 `schema_version`。未登记、非 active 或不可用的能力不得静默降级为通用引擎，应转真人例外并记录能力缺口。

当前本地能力登记表已覆盖规则、数据操作、外部系统、通知、内容和通用执行的演示能力；节点和子任务会携带冻结版本。现有 `service_ref` 前缀回退仅用于兼容历史模板和本地样例，不是生产环境的选派依据。平台配置管理组后续提供真实能力字典、登记表、启停/改派/回退门禁后，L2 以只读方式加载该配置，不自行发现或启用服务。

## 2026-07-20 v2.2 框架对齐更新

以《AI平台架构框架说明_v2_2_20260716》为准，L2 已将两张配置在运行模型中分开：

- `CapabilityDefinition` 是全平台能力字典，只定义统一的 `capability_id`、字典版本和启用状态；它不记录路由。
- `CapabilityRegistration` 是业务引擎层就地加载的能力登记，只定义 `capability_id -> service_code / action / schema_version` 的承办接线，并记录登记版本、状态、允许调用方和并发上限。
- `EngineService` 仅表示已部署的承办引擎服务。流程实例启动时选择并冻结三者的快照；后续配置改派不会改变已创建实例的节点或子任务。

正式能力指令可携带 `command_id`、`capability_ids`、参数、依赖关系、风险与确认标记。L2 不重新分析语义，也不重排意图引擎已经给出的依赖：输入依赖产出的节点串行，无依赖节点可并行。能力未登记、字典或登记非 `active`、或要求的意图确认未完成时，启动被拒绝，不回退到通用引擎。

平台适配层同时按 v2.2 收紧入口：带 `capability_ids` 的 `flow.start` 只接收 `l2.intent_analysis` 经 `l2_internal` 交接的已确认结构化指令。L4 的自然语言业务请求不再直接进入工作流引擎，而应先由业务引擎层接口控制模块分流给意图分析引擎；L4 的业务页面确定性请求由层接口分派到对应引擎，不把流程执行引擎当作总入口。`business.submit` / `task.submit` 保留为历史本地协议名的说明，不再是本适配器可执行路由。

本地 JSON 仓库仍仅用于可测试演示；生产状态持久化、能力登记运行期确认/回退、真实权限判定、接口控制模块转发以及跨进程 outbox/inbox 恢复均需在平台联调时由相应模块提供，L2 不直接访问共享数据库。
