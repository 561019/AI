# 汉和 AI 平台层间通信与权限协议

**版本：** v0.6（v2.2 联调执行基线）  
**日期：** 2026-07-15  
**适用范围：** L4 业务应用层、L2 业务引擎层、L1 基础模块层，以及接入三层的全部模块。  
**依据：** 《AI平台架构框架说明 v2.2》《v2.2 架构冲突解决与落地决议 v0.1》《层接口对内通道设计与模块接入规范 v0.1》。早期架构图仅作历史参考，不得与本协议冲突。

**最新口径：** v2.2 为当前唯一架构说明；意图分析与流程执行为两个命令中枢，只有流程执行引擎可以向执行引擎群派发子任务；创建类请求不再走 L4 直达 L1 的特殊路径；能力字典和能力登记表是引擎选派的唯一依据。

## 1. 目的和边界

本协议规定各层和各模块如何传递数据、返回结果、校验权限、追踪调用和处理失败。它不定义某一业务模块的业务字段；业务字段由各模块在服务目录登记的 `action` 对应 Schema 中定义。

本协议用于让不同小组独立开发后能够按同一规则接入，不允许以“先能跑”为由绕过层接口、权限校验、服务目录或审计留痕。

### 1.1 v2.2 强制扩展

- 自然语言经意图分析后必须输出 `capability_ids`、`capability_dictionary_version`、`requires_user_confirmation`、风险等级和依赖关系；流程执行按冻结的能力登记版本选派服务。
- `requires_user_confirmation=true` 时，意图确认未闭环不得进入 `flow.start`。高风险、写入、审批、资产创建/开放、对外发布必须为 `true`；低风险只读、纯查询和确定性表单可按登记规则为 `false`。
- 服务发现只产生 `discovered` 记录；只有契约、权限、安全、健康和回退门禁通过并经配置确认的记录才可 `active`。
- 所有数据写入声明 `storage_class`、`owner_service`、`retention_policy`、`trace_id/task_id`；未终态任务所需临时引用不得清理。

### 1.2 当前调用方向

```text
L4 应用/工作台 -> L4 接口 -> L2 接口 -> L2 业务引擎
                                      -> L2 接口 -> L1 接口 -> L1 基础模块
```

- 日常业务请求只允许由 L4 向 L2 发起，再由 L2 向 L1 发起；结果沿原调用链反向返回。
- L4 不直接调用 L1；L1 不向上层主动发起业务请求。
- L2 同层模块不得直接互调，必须由 L2 接口的对内通道转发。
- L1 内部模块的具体协作规则由 L1 服务目录和接口控制模块执行，不得暴露给 L4。
- 长任务办结后，由 L2 经 L4 接口向相关用户送达结果、待办或通知。
- 按 v2.1，创建 agent、技能、知识库等数字资产的请求也必须由流程执行引擎经 L2 对内通道交数字资产引擎办理，不存在 L4 直达 L1 的创建类特殊旁路。

### 1.3 三类请求入口

| 请求来源 | 入口形态 | L2 处理方式 |
| --- | --- | --- |
| 对话框 | 自然语言文本 | 交给意图分析引擎形成待确认意图；确认后交流程执行引擎，再由其派发子任务。 |
| 业务页面 | 格式化业务请求 | 交流程执行引擎创建/恢复流程；由流程执行引擎按节点派发承办引擎，不允许页面指定执行引擎直达。 |
| 待办、回调、定时触发 | 格式化系统请求 | 由登记服务校验来源后进入对应 L2 引擎，不伪装成用户自然语言请求。 |

## 2. 通信原则

1. 第一阶段统一使用 HTTP + JSON；服务端必须提供健康检查和版本信息接口。
2. 每个请求必须先通过接收层接口的格式、服务准入、调用方和权限校验，之后才允许转发。
3. 每次转发产生新的 `message_id`，但同一用户任务的 `trace_id` 不变。
4. 每个可执行动作必须在服务目录登记，未登记的服务或动作一律拒绝。
5. 模块只接收与自身职责相符的 `action`，不以通用透传接口接收任意业务数据。
6. 业务数据、模型输入、文件内容不应写入接口日志正文；日志只记录引用、摘要、长度、标签和审计编号。
7. 所有日期时间使用 ISO 8601 带时区格式；所有编码使用 UTF-8；金额、数量、计量单位必须在业务 Schema 中显式声明。

## 3. 公共请求信封

所有层间、层内转发请求均使用以下信封。`payload` 是唯一允许承载模块业务字段的位置。

```json
{
  "protocol_version": "1.0",
  "message_id": "msg_01JX...",
  "trace_id": "trace_01JX...",
  "request_id": "req_01JX...",
  "parent_message_id": "msg_01JW...",
  "occurred_at": "2026-07-14T14:30:00+08:00",
  "source": {
    "layer": "L2",
    "service_code": "l2.workflow_automation"
  },
  "target": {
    "layer": "L1",
    "service_code": "l1.template_management"
  },
  "channel": "cross_layer",
  "action": "template.retrieve",
  "request_type": "query",
  "actor": {
    "person_id": "person_001",
    "position_ids": ["position_finance_manager"],
    "digital_employee_id": null,
    "tenant_id": "tenant_hanhe"
  },
  "context": {
    "conversation_id": "conv_001",
    "task_id": "task_001",
    "data_refs": [],
    "purpose": "new_flow_start"
  },
  "idempotency_key": "template-retrieve-task-001",
  "deadline_at": "2026-07-14T14:30:15+08:00",
  "payload": {}
}
```

### 3.1 公共字段规则

| 字段 | 规则 |
| --- | --- |
| `protocol_version` | 必填。接口不兼容修改时提升主版本。 |
| `message_id` | 必填。每一次接口接收或转发均生成新值，全平台唯一。 |
| `trace_id` | 必填。一个用户任务、流程实例或系统触发任务从开始到结束保持不变。 |
| `request_id` | 必填。发起方生成，标识一次业务请求；用于用户侧查询和幂等处理。 |
| `parent_message_id` | 首次请求为空；转发或回调时必填，用于还原调用关系。 |
| `source` / `target` | 必填。层级和 `service_code` 必须与服务目录一致。 |
| `channel` | 取值为 `l4_to_l2`、`l2_internal`、`cross_layer`、`callback`、`scheduled`。 |
| `route_type` | L2 对内通道必填：`command.handoff`、`task.dispatch` 或 `flow.callback`；其他组合拒绝。 |
| `capability_id` | L2 命令和子任务必填；必须与冻结的能力字典版本和能力登记表匹配。 |
| `capability_dictionary_version` / `registry_version` | 进入流程的命令必填；流程实例冻结该版本，运行中不得无声切换承办服务。 |
| `action` | 必填，采用 `领域.动作` 格式，例如 `intent.analyze`、`template.retrieve`、`model.generate`。 |
| `request_type` | 必填，取值为 `query`、`execute`、`maintain`。服务目录必须声明允许类型。 |
| `actor` | 由接口控制模块根据已认证会话或数字员工身份注入；前端和业务模块不得自行伪造。 |
| `context.data_refs` | 只传数据引用、数据标签、版本和允许动作；不得默认复制敏感原文。 |
| `idempotency_key` | `execute` 和 `maintain` 必填。接收方须保证同一调用方、动作和键重复提交不重复执行。 |
| `deadline_at` | 必填。接收方超过截止时间不得继续无限等待，应返回标准失败或受理回执。 |

### 3.2 身份与数字员工

- `actor.person_id` 是最终责任真人；日常业务请求必须存在。
- 数字员工执行任务时，必须同时携带 `digital_employee_id` 和授权其运行的 `person_id`，不得以数字员工替代责任真人。
- L1.8 账号网关负责身份认证、账号生命周期和会话凭据；业务模块只消费经接口控制模块验证后的身份上下文。
- 岗位不是身份替代品。请求可带多个 `position_ids`，但权限结论针对具体真人及其当前任职、上下级关系和制度依据作出。

## 4. 三种标准回复

平台仅使用三种业务语义的标准回复。无论成功、拒绝、格式错误、权限拒绝还是模型故障，都必须返回符合本节结构的 JSON。

| `reply_type` | 含义 | L4 行为 |
| --- | --- | --- |
| `success` | 即时结果，当前请求已办结。 | 展示结果或刷新对应业务页面。 |
| `accepted` | 受理回执，任务已登记但尚未办结。 | 展示处理中状态；等待 L2 后续通知或查询。 |
| `failed` | 拒绝及原因，未受理或处理失败。 | 显示可理解的原因；按 `retryable` 决定是否允许重试。 |

### 4.1 统一回复结构

```json
{
  "protocol_version": "1.0",
  "reply_type": "success",
  "message_id": "msg_01JY...",
  "trace_id": "trace_01JX...",
  "request_id": "req_01JX...",
  "in_reply_to": "msg_01JX...",
  "service_code": "l1.template_management",
  "service_version": "1.0.0",
  "occurred_at": "2026-07-14T14:30:01+08:00",
  "result": {
    "result_type": "data",
    "data": {}
  },
  "error": null,
  "audit": {
    "decision_id": "decision_01JX...",
    "event_id": "audit_01JY..."
  }
}
```

### 4.2 `accepted` 的最小结果

```json
{
  "result": {
    "result_type": "task_receipt",
    "task_id": "task_001",
    "status": "accepted",
    "status_query_action": "task.get",
    "estimated_completion_at": "2026-07-14T14:35:00+08:00"
  }
}
```

### 4.3 `failed` 的最小错误

```json
{
  "error": {
    "code": "permission_denied",
    "message": "当前操作不具备所需权限。",
    "retryable": false,
    "retry_after_seconds": null,
    "details": {
      "denial_reason": "policy_not_satisfied"
    }
  }
}
```

错误码采用稳定英文标识；面向用户的中文说明由 L4 按错误码和场景展示。至少统一包含：`invalid_message`、`unsupported_protocol_version`、`service_not_registered`、`action_not_allowed`、`caller_not_allowed`、`permission_denied`、`resource_not_found`、`conflict`、`timeout`、`dependency_unavailable`、`internal_error`。

### 4.4 状态与回复的对应关系

| 业务状态 | 允许回复 | 必须持久化 | 责任方 |
| --- | --- | --- | --- |
| 即时办结 | `success` | 结果摘要、引用、审计事件 | 当前承办服务。 |
| 已受理/处理中 | `accepted` | `task_id`、状态、责任真人、查询动作、幂等键 | 创建任务的服务；流程任务由流程执行引擎负责。 |
| 已拒绝/失败 | `failed` | 稳定错误码、是否可重试、失败阶段、审计事件 | 拒绝或检测到失败的接口/服务。 |

`accepted` 不能只作为 HTTP 202 使用而不建立任务记录；`success` 不能表示“已进入后台处理”。状态迁移必须由状态责任方执行，其他模块只能提交回执或决定。

## 5. 权限通信协议

### 5.1 职责分工

| 能力 | 负责模块 |
| --- | --- |
| 认证、账号、会话、数字员工账号 | L1.8 账号网关 |
| 岗位、任职、上下级、数据/资源权限与制度化授权判定 | L1.1 权限管理 |
| 脱敏、输入输出红线、越权告警、不可篡改审计 | L1.9 安全合规 |
| 请求接收、权限执行点、服务准入和转发留痕 | L4/L2/L1 接口控制模块 |

接口控制模块是权限执行点：每次规定转发前向 L1.1 请求决策；L1.1 是权限决策点。权限决策调用是为避免递归而允许的直达基础调用，但必须携带 `trace_id` 并记录审计事件。

### 5.2 权限决策请求

```json
{
  "trace_id": "trace_01JX...",
  "decision_request_id": "pdp_01JX...",
  "subject": {
    "person_id": "person_001",
    "position_ids": ["position_finance_manager"],
    "digital_employee_id": null
  },
  "action": "template.publish",
  "resource": {
    "resource_type": "flow_template",
    "resource_id": "expense_travel_approval",
    "data_labels": ["internal"],
    "state": "draft"
  },
  "context": {
    "tenant_id": "tenant_hanhe",
    "management_domain": "finance",
    "occurred_at": "2026-07-14T14:30:00+08:00",
    "purpose": "publish_template"
  }
}
```

权限判断必须覆盖“什么时间、谁、对哪一个数据或资源、做哪一个动作”四要素，并以岗位任职、上下级关系、已有授权和制度依据为输入。无明确依据时默认拒绝。

### 5.3 权限决策回复

```json
{
  "decision_id": "decision_01JX...",
  "allow": true,
  "policy_refs": ["policy.template.publish.v1"],
  "obligations": [
    {"type": "human_confirmation_required"},
    {"type": "audit_required"}
  ],
  "denial_reason": null,
  "decided_at": "2026-07-14T14:30:00+08:00"
}
```

- `allow=false` 时，接口控制模块不得转发原请求。
- `obligations` 是放行附带条件；例如脱敏、仅只读、必须真人确认、不得外发。接收模块必须执行，不得忽略。
- L1.1 记录决策输入摘要、结论、制度/策略依据；L1.9 记录安全和合规事件；业务模块记录业务办理事件。

## 6. 服务目录与模块 Schema

每个模块接入前必须向平台服务目录提交如下登记信息：

```json
{
  "service_code": "l2.content_generation",
  "service_name": "内容产出引擎",
  "layer": "L2",
  "owner_group": "L2 内容产出组",
  "status": "active",
  "actions": [
    {
      "name": "content.generate",
      "request_type": "execute",
      "input_schema_version": "1.0",
      "output_schema_version": "1.0",
      "allowed_callers": ["l2.intent_analysis"],
      "required_permission_actions": ["content.generate"],
      "data_labels_supported": ["internal"],
      "timeout_seconds": 30,
      "async_supported": true
    }
  ],
  "health_check": "/health"
}
```

模块组除公共信封外，必须为每个 `action` 提供：

1. 输入 JSON Schema、输出 JSON Schema、示例请求和三种标准回复样例。
2. 动作对应的资源类型、数据标签、权限动作和制度依据。
3. 同步超时、重试边界、幂等规则、是否可异步受理。
4. 返回结果类别：`data`、`artifact_ref`、`task_receipt`、`decision`、`notification_receipt` 之一。
5. 所有敏感原文的引用方式和脱敏要求，不得以“任意 JSON”规避 Schema。

## 7. 各层通信规则

### 7.1 L4 与 L2

- L4 只调用 L4 接口；L4 接口只向 L2 服务目录登记的入口转发。
- L4 请求可为自然语言或格式化请求，必须带用户会话、发起真人、界面场景和 `request_id`。
- L4 不决定业务引擎、模型、数据源、审批人或旧系统凭据。
- L2 的 `accepted`、办结结果、待办和通知由 L4 接口按 `trace_id` 与 `request_id` 回送到用户界面。

### 7.2 L2 层内

- 意图分析引擎只输出任务理解和经本人确认的结构化指令，不派发执行引擎。
- 流程执行引擎是唯一执行组织者，负责流程实例、任务拆分、编排、暂停、续办、回调和向执行引擎群派发子任务；固定审批流程从 L1.2 取模板并锁定版本。
- 执行引擎群只完成流程执行引擎派发的子任务，返回结果或受理回执，不相互调用。
- 层内转发仍使用公共信封，`channel` 必须为 `l2_internal`，以便审计和责任定位。

#### 7.2.1 L2 对内通道的路由白名单

| 来源服务角色 | 目标服务角色 | 允许动作类型 | 接收方可改变的状态 |
| --- | --- | --- | --- |
| 意图分析 | 流程执行 | `flow.start`，载荷为已确认结构化命令 | 仅流程实例/节点/子任务状态。 |
| 流程执行 | 任一执行引擎 | 该引擎已登记的子任务动作，例如 `content.generate` | 仅自己的子任务/产物状态。 |
| 任一执行引擎 | 流程执行 | `flow.callback` 或登记的同步回执 | 仅流程执行可推进流程和节点。 |
| 流程执行 | 监控提醒 | `notification.dispatch`、`monitor.subscribe` | 仅通知投递状态。 |

`l2_internal` 只是传输信道，不是普通 RPC 总线。服务目录必须按上表校验来源、目标和动作三元组；例如 `l2.intent_analysis -> l2.content_generation : content.generate`、任一执行引擎之间的调用均返回 `caller_not_allowed`。

### 7.3 L2 与 L1

- L2 通过 L2 接口和 L1 接口访问 L1；L1 接口仅接受目录白名单中的 L2 调用方。
- L1 返回能力结果、数据引用、策略决策、任务回执或失败，不返回面向最终用户的页面内容。
- L2 负责把 L1 能力结果组织为业务结果、流程状态或待办；L4 负责展示。
- 模型调用只能使用 L1.5；旧系统读写只能使用 L1.10；真实权限判断只能使用 L1.1；不得绕过相应基础模块。

### 7.4 长任务、通知与回调

- 超过同步截止时间仍可安全继续的任务返回 `accepted`，并持久化 `task_id`、`trace_id`、责任真人和当前状态。
- 子任务完成、人工待办、超时和失败均以 `callback` 信道回到 L2 流程或原发起引擎；不得直接推送到 L4。
- L2 判断需要通知后，经 L4 接口送达 L4 待办、预警、结果或真人拍板任务。
- 回调必须携带原始 `trace_id`、`task_id`、`parent_message_id` 和幂等键；重复回调不得重复改变业务状态。

## 8. 第一阶段最小联调链路

```text
L4 对话页面
  -> L4 接口：校验、身份注入、权限决策、留痕
  -> L2 接口：服务准入、权限决策、留痕
  -> L2.1 意图分析：与本人确认并输出结构化命令
  -> L2 接口对内通道 -> L2 流程执行引擎：创建实例、权限决策、留痕
  -> L2 接口对内通道 -> L2 内容产出引擎：流程执行引擎派发子任务
  -> L2 接口 -> L1 接口：权限决策、留痕
  -> L1.5 大模型调度
  -> 按原链返回 L4
```

该链路至少验证：

1. 同一 `trace_id` 能串起所有请求、回复、权限决策和审计事件。
2. 每次转发都有对应 `decision_id`，无权请求不进入下一跳。
3. 正常生成返回 `success`；长任务返回 `accepted`；权限拒绝和模型故障返回 `failed`。
4. 意图分析与内容产出之间不存在直接调用记录；中间必须有流程实例和子任务记录。
5. 模型输入只从 L1.5 发出；页面没有直连 L2 引擎、L1 模块或模型服务。

## 9. 协议变更与验收

- 公共信封、标准回复、权限请求和服务目录结构由架构组维护，修改须提升 `protocol_version` 并记录兼容性结论。
- 模块业务 Schema 由模块组维护，修改须经架构组确认其不破坏层间边界、权限字段和追踪字段。
- 每个模块合入主链路前必须通过：Schema 校验、成功/受理/失败三类回复测试、权限放行/拒绝测试、`trace_id` 透传测试、健康检查和服务目录校验。
- 尚未取得权威定义的“六项指令”仅在服务目录的 `action` 层补充；不得为此修改本协议的公共信封和三种回复语义。

## 10. 待架构审定事项

1. L1.1 已冻结为权限管理；既有资料中的“创建层”不再作为模块分工依据。
2. 六项指令的业务名称可在服务目录附录继续补充，但不得改变公共信封、权限和调度规则。
3. L3 启用后的允许调用路径、服务准入与返回规则不在本版本范围内，启用前必须另行补充。

## 11. 联调落地要求

本节是各组执行本协议的最低交付要求。协议不是要求每组自行复制 JSON 结构；框架组必须提供统一代码和验证工具，模块组必须通过统一入口接入。

### 11.1 框架组必须交付的公共组件

框架组建立 `common/platform_contract/`，作为所有服务唯一允许使用的协议实现，至少包含：

| 组件 | 必须提供的能力 |
| --- | --- |
| `schemas` | 请求、回复、权限决策、服务目录的 Pydantic/JSON Schema 定义。 |
| `message_factory` | 生成 `message_id`、`trace_id`、时间戳和标准请求/回复。 |
| `validator` | 校验协议版本、必填字段、调用方向、服务目录和 Schema 版本。 |
| `error_codes` | 本协议规定的稳定错误码、HTTP 状态码和 L4 展示文案映射。 |
| `client` | L4/L2/L1 调用客户端；自动透传追踪字段、截止时间和父消息编号。 |
| `middleware` | FastAPI 中间件；在接口入口校验、注入追踪上下文、记录审计摘要。 |
| `audit` | 统一记录请求摘要、回复摘要、权限决策编号、耗时和结果状态。 |
| `testkit` | Mock 服务、样例报文、契约测试断言和端到端链路测试工具。 |

模块组不得复制或修改公共信封结构。需要新增字段时，只能向架构组提出 Schema 变更申请。

### 11.2 固定 HTTP 入口

第一阶段所有服务使用以下固定入口。业务 `action` 写入请求信封，不把动作名称散落到临时 URL 中。

| 入口 | 方法 | 调用方 | 用途 |
| --- | --- | --- | --- |
| `/health` | `GET` | 平台、测试、运维 | 返回服务是否可用、服务版本和服务目录状态；不返回敏感配置。 |
| `/api/v1/capabilities` | `GET` | 层接口、测试 | 返回已登记的 `service_code`、`action`、Schema 版本和状态。 |
| `/api/v1/instructions` | `POST` | 上层接口或本层对内通道 | 接收本协议第 3 节定义的公共请求信封。 |
| `/api/v1/callbacks` | `POST` | 已登记下游服务 | 接收长任务、人工待办、超时和子任务状态回调。 |

- HTTP 只负责传输，业务结论以回复体的 `reply_type` 和错误码为准。
- 请求校验失败使用 HTTP `400`；身份未认证 `401`；权限拒绝 `403`；服务或动作未登记 `404`；幂等冲突 `409`；受理任务 `202`；即时成功 `200`；内部或依赖错误 `5xx`。
- `POST /api/v1/instructions` 只接受 `application/json; charset=utf-8`。
- `trace_id`、`request_id`、`message_id` 必须同时写入回复体；可额外写入 HTTP 响应头供网关和日志系统使用，但回复体是权威来源。

### 11.3 每个模块的最小服务骨架

每个模块必须按以下顺序实现，业务代码只能放在第 5 步：

1. 使用公共 `schemas` 解析请求，拒绝不合规报文。
2. 校验本模块是否登记了目标 `action`，以及调用来源是否在白名单。
3. 接收接口控制模块注入的身份、权限决策编号和义务；不自行信任前端传来的身份字段。
4. 写入开始审计事件，并设置超时/幂等保护。
5. 执行本模块登记的业务能力。
6. 将结果转换为公共回复，写入结束审计事件。
7. 长任务创建受理记录后返回 `accepted`；后续只经回调接口报告状态。

模块业务函数的建议边界如下：

```python
def handle_action(payload: dict, context: ExecutionContext) -> ActionResult:
    """只处理本模块的业务字段，不解析 HTTP，不伪造身份，不自行跨层调用。"""
```

### 11.4 接口控制模块的强制职责

L4、L2、L1 接口控制模块由框架组统一实现或使用同一公共中间件，必须执行以下顺序：

```text
接收请求
-> 协议校验
-> 认证身份并注入真人/数字员工上下文
-> 查询服务目录和调用方向
-> 请求 L1.1 权限决策
-> 执行 L1.9 返回的安全义务
-> 创建审计事件
-> 转发到登记目标
-> 校验目标回复
-> 记录结果并沿原路返回
```

其中任何一步失败，接口控制模块返回标准 `failed`，不得将未经校验的原始请求直接透传给模块。

### 11.5 模块联调准入包

每个小组在申请接入联调前，向架构组提交一个目录，内容必须齐全：

```text

  schemas/
    action-name.input.schema.json
    action-name.output.schema.json
  examples/
    success.request.json
    success.response.json

    failed.response.json
  tests/

    test_permission.py
    test_idempotency.py
  README.md
```

README 至少说明：模块负责什么、不负责什么、允许的调用方、需要的数据引用、输出结果类型、权限动作、超时、重试、负责人和当前版本。

### 11.6 契约测试和联调门禁

框架组提供一条统一命令，例如：

```powershell
python -m platform_contract.testkit verify-module path\to\module-name
```

只有以下检查全部通过，模块才可以登记为 `active` 并接入主链路：

- 公共请求和三种回复 Schema 校验通过。
- `trace_id`、`request_id`、父消息关系正确透传。
- 未登记服务、错误调用方、错误协议版本均被拒绝。
- 权限放行、权限拒绝和附带义务均被执行并留下 `decision_id`。
- `execute`、`maintain` 动作重复提交不重复执行。
- 超时、下游不可用和异常返回标准 `failed`，不暴露堆栈或敏感信息。
- `/health` 和 `/api/v1/capabilities` 可用，服务目录与实际动作一致。
- 模块不包含对 L1 模型、旧系统、其他 L2 引擎或其他模块数据库的未登记直连。

## 12. 各层与各模块标准动作目录

### 12.1 L4 对 L2 的应用接口

| `action` | 调用路径 | 输入 `payload` 最小字段 | 标准结果 |

## 13. 数据引用、结果包装与流转模式

### 13.1 数据引用标准

跨模块默认传递 `data_ref` 或 `artifact_ref`，而不是复制原始敏感数据。引用对象最小结构如下：

```json
{
  "ref_id": "dataref_001",
  "source_system": "erp_e10",
  "resource_type": "sales_detail",
  "resource_ids": ["2026-07-sales"],
  "version": "snapshot_20260714_001",
  "data_labels": ["internal"],
  "allowed_actions": ["read", "aggregate"],
  "lineage": ["source:erp_e10", "aggregate:l2.data_aggregation"]
}
```

- L1.7 和权威旧系统负责引用指向的数据真实性；L2 不复制形成另一份权威数据。
- 需要把内容送入模型、沙箱或外部系统前，必须再次依据当前动作和数据标签请求 L1.1 权限决策，并执行 L1.9 的脱敏/合规义务。
- `artifact_ref` 用于文件、图片、音视频和报告产物，必须包含版本、来源、校验值、存储位置和访问标签。

### 13.2 结果包装规则

所有模块业务结果只能使用以下类别：

| `result_type` | 使用场景 | 必备内容 |
| --- | --- | --- |
| `data` | 查询、计算、问答、内容草稿 | 结构化结果或可见摘要、来源/版本/引用。 |
| `artifact_ref` | 文档、表格、图片、音视频、报告 | 产物引用、格式、版本、校验和访问标签。 |
| `task_receipt` | 长任务、流程、旧系统写入、沙箱执行 | `task_id`、状态、查询动作、预计完成时间。 |
| `decision` | 权限、合规、成本、运行约束 | `allow`、`decision_id`、依据、义务或拒绝原因。 |
| `notification_receipt` | 待办、预警、通知 | 通知编号、目标、状态、关联任务/流程。 |

### 13.3 自然语言内容产出流

```text
L4 chat.send(text)
  -> 意图分析 intent.analyze / intent.confirm
  -> flow.start（流程执行引擎）
  -> 内容产出 content.generate（由流程执行引擎派发）
  -> L1.6 context.resolve / prompt.render
  -> L1.13 knowledge.retrieve（需要知识时）
  -> L1.9 inspect_input
  -> L1.5 model.generate
  -> L1.9 inspect_output
  -> 内容产出包装内容草稿与引用
  -> L4 展示 success 或 accepted
```

结果必须保留内容版本、模型调用摘要、知识引用和合规结论；L4 只展示被授权且已通过合规检查的结果。

### 13.4 数据查询与分析流

```text
L4 business.submit / chat.send
  -> 意图分析（自然语言时）或流程执行的确定性指令认领入口（格式化请求时）
  -> L1.1 permission.decide(data.read)
  -> L1.7 data.locate / data.read
  -> 流程执行派发数据操作（读/写/归集汇总）
  -> 流程执行派发规则计算或分析预测
  -> L1.9 合规检查
  -> L4 返回数据摘要、报表引用和血缘
```

数据读取先定位、再逐次权限校验；结果必须标注口径、数据时间范围、来源和异常/缺失信息。AI 分析结果不得覆盖确定性规则计算结果。

### 13.5 固定审批流程与人工确认流

```text
L4 business.submit
  -> flow.start（流程执行引擎）
  -> L1.2 template.retrieve（锁定模板版本）
  -> L1.1 position.resolve / permission.decide
  -> 流程执行引擎执行自动节点和条件分支
  -> L1.11 human_task.create
  -> L4 展示待办
  -> L4 human.decide
  -> 流程执行引擎继续、驳回或结束流程
```

模板只保存岗位，不保存具体审批人；运行时由 L1.1 按当前任职、上下级、制度和权限解析真人。人工决定必须记录真人、时间、意见、附件引用和模板版本。

### 13.6 旧系统读取与写入流

```text
L2 形成已授权系统动作
  -> L1.1 permission.decide(system.read / system.write)
  -> L1.9 安全/脱敏/外发检查
  -> L1.10 system.read 或 system.write(operation_id)
  -> 旧系统
  -> L1.10 返回外部回执、状态和结果引用
  -> L2 更新任务/流程状态
  -> L4 展示结果或等待状态
```

- `system.write` 必须携带不可重复的 `operation_id`，并记录外部系统回执；重试必须使用同一 `operation_id`。
- 资金、合同、用印、对外发布和其他关键经营动作必须先完成固定模板和真人确认，不得由 AI 直接写入。
- 旧系统账号和密钥只由 L1.10 的部署配置持有，不出现在 L4、L2 `payload`、日志或提示词中。

### 13.7 异步回调与通知流

```text
下游模块/旧系统完成或超时
  -> callback(trace_id, task_id, parent_message_id, result)
  -> 流程执行引擎 / 原发起 L2 引擎
  -> 监控提醒引擎判断订阅、提醒和催办
  -> L4 notification.list / task.get
```

回调只改变与自身 `task_id` 和状态迁移规则匹配的任务；重复、过期或来源未登记的回调必须拒绝并留痕。通知是 L2 向 L4 的业务结果，不允许下游服务绕过 L2 直接推送用户。

## 14. 接口交付责任

| 接口类型 | 谁定义公共结构 | 谁定义业务 Schema | 谁实现 | 谁验收 |
| --- | --- | --- | --- |
| L4 应用接口 | 架构组 | L4 组 + 对应 L2 组 | L4 组、架构组接口控制模块 | 架构组、测试组、业务方。 |
| L2 层内接口 | 架构组 | 发起/承办 L2 组共同提交 | L2 接口控制模块 + 承办组 | 架构组、测试组。 |
| L2 -> L1 接口 | 架构组 | L1 能力组，L2 调用组确认 | L1 接口控制模块 + L1 组 | 架构组、测试组。 |
| 权限/身份/安全接口 | 架构组 + L1.1/L1.8/L1.9 组 | L1.1/L1.8/L1.9 组 | 对应 L1 组 | 架构组、安全/测试组。 |
| 旧系统适配接口 | 架构组 + L1.10 组 | L1.10 组 + 业务系统负责人 | L1.10 组 | 架构组、业务方、测试组。 |

各模块必须将本节相应动作写入服务目录并附输入/输出 Schema。架构组负责公共协议和调用路径，不替模块组替写其业务字段或业务规则。
