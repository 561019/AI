# 数据操作引擎：研发迭代与进化记录

版本：v0.5  
日期：2026-07-29  
维护范围：`2.4数据归集聚合引擎` 项目目录  

## 1. 交接结论

本模块原名“数据归集聚合引擎”，现按平台职责定位为**数据操作引擎**。它不是统计、分析或规则计算引擎，而是业务和过程数据进入 L1.7 数据模块前的唯一 L2 业务入口：负责登记、打标签、受控读写、版本更新、逻辑删除和变化追溯。

当前代码已经形成可联调的本地闭环，但数字资产引擎、文档表格解析引擎和 L1.13 知识库模块仍由其他模块接入。不得把“已生成后续任务提示”表述为“已完成跨模块真实调用”。

## 2. 迭代主线

### 阶段一：从“归集汇总”转向“数据操作”

早期实现聚焦多公司数据归集和汇总，旧代码中仍保留 `data.aggregate` 与自然语言聚合入口，供历史测试兼容。后续职责被澄清：

- 数据操作引擎只处理业务数据的收集、整合、增、删、改与登记；
- 规则计算归规则计算引擎，分析预测归分析预测引擎；
- 引擎不能由 L4 自然语言直接驱动，也不能自行编排流程；
- 正式任务只能由流程执行引擎经 L2 对内通道派发。

因此，正式 HTTP 入口收敛为 `POST /api/l2/tasks`。旧 `/api/l4/parse`、`/api/l4/execute`、`/api/l2/requests` 统一返回 `410 LEGACY_ENDPOINT_DISABLED`，避免绕过意图分析和流程执行。

### 阶段二：明确“两本账”和存储边界

平台确认：对话、上下文、表格、PDF、AI 生成物、解析结果、Agent/Skill 的代码与配置等，只要需要持久留存，都属于业务或过程数据。

据此形成两本账：

| 账本 | 责任方 | 记录内容 |
| --- | --- | --- |
| 业务资产账 | 数据操作引擎 | `data_ref`、业务类型、标签、来源、公司范围、版本、状态、变化事件 |
| 仓管账 | L1.7 数据模块 | `data_ref`、物理 URI、内容哈希、物理状态、版本文件 |

数据操作引擎生成 `data_ref`；L1.7 返回 `storage_uri` 和内容哈希。二者不可混用。数字资产引擎管理 Agent、Skill、知识库的身份、登记和生命周期，但不直接保存代码、PDF 或普通业务文件到 L1.7。

### 阶段三：把“持久化”做成受控动作

`data.persist`、`data.update`、`data.delete` 均要求当前真人、公司范围、权限检查、安全检查和审计留痕。固定留存还必须携带 `approval_ref` 或 `retention_policy_ref`。

实现变化包括：

- `data.persist` 实际调用可替换的 L1.7 本地适配器写入 JSON 内容及可选二进制文件；
- 文件元数据包含文件名、媒体类型、大小、SHA-256 和 `storage_uri`；
- `data.update` 写新版本，不覆盖历史版本；
- `data.delete` 为逻辑删除，保留历史证据；
- 写入失败时清理刚创建的本地二进制文件，降低孤儿文件风险；
- `data.trace` 同时返回资产账、仓管账与变化事件，验证同一 `data_ref` 的关联。

### 阶段四：纠正知识库文件链路

此前“原始 PDF 保存后立即触发索引”的设计错误：原始文件不能直接切片和向量化。现已修正为：

```text
knowledge_source_file（PDF 原件）
  → data.persist / L1.7 保存
  → flow.callback: document.parse（parse 或 reparse）
  → 文档表格解析引擎产出正文、章节、表格
  → parsed_document 经 data.persist 保存
  → flow.callback: asset.knowledge_source.sync
  → 数字资产引擎 → L1.13 切片、向量、检索索引
```

知识源和解析结果必须携带：

```json
"knowledge_binding": {
  "kb_asset_id": "KB-001",
  "kb_instance_ref": "kb-instance-001"
}
```

这是为了使后续索引任务可以精确定位目标知识库。缺失该绑定，任务会以 `KNOWLEDGE_BINDING_REQUIRED` 失败。

### 阶段五：防止任务回执变成文件泄露通道

最初的本地读取实现允许 `include_artifact_content=true`，会把文件 Base64 进入任务回执和数据库记录。这不适合正式联调：大文件会膨胀任务数据，也会扩大泄露面。

现已禁止该行为：`data.read` 仅返回内容对象、文件元数据和 `storage_uri`；需要文件本体的解析器应通过 L1.7 的受控读取接口，按 `data_ref` 获取。若在 L2 任务中请求内联文件内容，返回 `ARTIFACT_INLINE_CONTENT_FORBIDDEN`。

### 阶段六：补齐可手动演示的数据生命周期界面

后端已具备 `data.collect`、`data.persist`、`data.search`、`data.read`、`data.update`、`data.delete`、`data.trace`、`data.consolidate` 八个动作，但旧控制台只能演示自然语言查询。为避免“后端具备、界面无法证明”的断层，新增“业务数据管理”视图。

该视图不会直接写 L1.7：它明确以“流程执行本地模拟派单”身份组装标准 `task.dispatch`，调用 `/api/l2/tasks`，接收并确认 `flow.callback`，再展示标准回执和审计链。这样前端可演示完整生命周期，但不改变正式环境由流程执行引擎派单的职责边界。

### 阶段七：为案例九补齐通用结构化取数与确认审计

案例九要求验证经营诊断、预测和第三方确认的跨模块链路。最初风险是为案例九把比例计算、归因或预测逻辑硬编码进本模块；这会破坏“数据操作引擎即插即用”的边界。因此本次只实现通用能力：

- `data.search + query_spec`：受控读取 `business_record_table`，支持字段选择、过滤、分组、计数、去重计数和排序；不支持比例、环比、归因或预测；
- `runtime_decision_audit`：仅保存当前真人的确认/拒绝、关联上游结果引用、主题、时间和业务关联编号；禁止写入或覆盖分析、预测和计算结论；
- `case9_fixture.py`：作为本地脱敏联调夹具，通过正式 `data.persist` 写入案例数据；核心引擎不依赖 `scenario=case9`；
- 启动参数 `--seed-case9`：仅供本地演示加载夹具，不代表已接入真实经营数据库；
- “业务数据管理”页新增 A1-A4、B1-B2、C1 手动分步入口。每一个按钮独立派发 `POST /api/l2/tasks`，展示 L1.7 `data.read` 授权、行预览、回执和页面内执行历史。

案例九中的职责边界必须按下列方式陈述：A/B 段本模块只取得诊断或预测的输入数据；复购率、环比等归规则计算引擎，原因归因和预测归分析预测引擎，能力选择归知识地图或流程执行相关模块；C 段本模块只留确认审计。

### 阶段八：补齐 PDF 等业务附件的网页存档入口

此前 L1.7 适配器已经支持 `artifact={filename, media_type, content_base64}`，并能保存二进制原件、生成 SHA-256、限制 10 MB、禁止在 L2 回执返回文件本体；但“业务数据管理”页没有文件选择控件，导致能力只能由 HTTP 请求证明，无法在网页演示。

本轮在“收集与固定存档”加入业务附件选择、文件名/类型/大小预检查、知识库源文件绑定字段和回执文件元数据展示。浏览器只把一个标准 `artifact` 放进既有 `data.persist` 或 `data.collect` 任务；L1.7 适配器仍负责 Base64 解码、物理保存、文件名净化和哈希校验。这保持了接口的深度和实现的局部性，前端不直接接触 L1.7 文件路径。

普通 PDF 可使用一般业务类型保存；若 PDF 是知识库来源，必须选择 `knowledge_source_file` 并填写 `kb_asset_id` 和 `kb_instance_ref`。保存后本模块只返回 `document.parse` 后续任务提示，绝不自行解析、切片或建立索引。

### 阶段九：消除更新和删除的目标对象歧义

原页面只把选中的 `data_ref` 填进“读取与追溯”输入框，更新和删除卡片本身没有显示目标对象。该设计要求操作人依赖记忆判断当前操作对象，存在误更新、误删除风险。

现已新增“当前操作对象”卡：从检索结果选择数据后，固定展示完整 `data_ref`、业务类型和标签；读取、更新、删除均作用于这张卡显示的对象。切换真人或手动清除时，选择自动失效；手动输入编号会标记为“未核验”；更新和删除均需二次确认。该控制只改变前端操作安全性，不改变后端的实时判权、审计和逻辑删除规则。

## 3. 当前可验证能力

| 动作 | 当前实现 | 验证重点 |
| --- | --- | --- |
| `data.persist` | 资产登记 + L1.7 固定存储 | `data_ref`、标签、仓管位置、文件元数据 |
| `data.read` | 按真人和范围受控读取 | 内容、版本、文件元数据；不返回文件 Base64 |
| `data.search` | 按标签、类型、公司范围检索 | 只返回登记元数据 |
| `data.search + query_spec` | 受控业务记录表读取、分组、计数、排序 | 物理读取经 L1.7 `data.read` 授权；不计算比例或预测 |
| `data.collect` | 登记已取得的业务内容 | 不执行解析或统计 |
| `data.consolidate` | 登记已完成整合的结果和来源 | 不承担汇总计算 |
| `data.update` | 新版本写入和事件留痕 | 历史版本不被覆盖 |
| `data.delete` | 逻辑删除和留痕 | 历史证据仍可追溯 |
| `data.trace` | 两本账和事件追溯 | `data_ref` 一致性 |
| `runtime_decision_audit` | 保存第三方确认/拒绝审计 | 只记录决定和上游结果引用，不改写业务结论 |

## 5. 未完成项与真实风险

1. 当前 L1.7、L1.1、L1.8、L1.9 和流程执行引擎均为本地 Mock；真实服务地址、鉴权方式和重试机制尚待联调。
2. 文档表格解析引擎、数字资产引擎、L1.13 知识库模块没有真实接入；本模块只通过 `downstream_task_hint` 给出下一步标准任务。
3. 二进制文件上传目前使用 Base64 且限制 10 MB，仅适合演示。生产应改为对象存储预签名上传或上传会话，不应继续把大文件放进 JSON 请求体。
4. 旧聚合代码仍在 `engine.py` 里，用于历史测试兼容；对外 HTTP 已禁用。后续如确认不再需要历史测试，可另开变更清理，不能在联调前贸然删除。
5. 案例九夹具是本地脱敏数据，且 A/B/C 上游引擎仍为外部 Mock；不得把界面展示成“完整经营诊断与预测已实现”。

## 6. 接手建议

接手者先阅读 `README.md`、`api_contract.md`、`数据操作引擎_工作成果使用手册_v0_4_20260727.md`，再运行测试。接入其他团队时，优先替换适配器和任务转发，不要让数据操作引擎直接调用同层引擎或直接访问 L1.13。任何重大改动（职责边界、接口字段、存储模型、演示链路或测试结论）必须同步更新本记录和使用手册。
## 7. 阶段十：纠正“原始字段即业务答案”的联调缺陷（2026-07-29）

老师联调指出，原回执若直接把 `extracted_fields` 或 `rows` 交给流程执行和内容产出，后续模块会拿样本猜答案，无法证明结果稳定、完整和可追溯。这不是展示问题，而是模块接口没有把“原始数据”“业务结果”和“证据”分开。

本次将结构化 `data.search` 升级为 `business-result.v1`：

- 流程派单新增 `query_spec.operation` 与 `query_spec.business_object`；数据操作引擎按固定任务执行，不自行猜业务语义。
- 主结果统一为 `business_result`，包含操作类型、业务对象、摘要、`items`、确定性 `metrics` 与警告。
- 证据统一为 `evidence`，包含源 `data_ref`、来源行引用和 `data.read` 权限决定。
- 原始访问统一为 `raw_access`，只给 `query_ref`、原始数量、源引用和受控样本；它不能作为内容产出答案材料。
- 新增 `extracted_fields` 行重组：仅按 `parse_job_id + sheet + row` 合并单元格；不通过字段名推断业务对象。

缺少 `operation` 或 `business_object` 的旧 `query_spec` 仍可运行，但会写入 `warnings`。这是过渡兼容，不是正式派单格式；联调方必须补齐两个字段。

确定性行重组、投影、分组、计数、求和、最大值、最小值、排序属于结果组装；比例、环比、趋势、归因、诊断和预测仍由规则计算或分析预测引擎承办。不要把“能组装业务结果”误报成“数据操作引擎可以做业务分析”。

验证：`node --check web/app.js`、`python -B -m unittest -q .\test_engine.py .\test_server.py`、`python -m json.tool .\openapi.json > $null` 均通过；后端共 44 项测试，包含单元格级 `extracted_fields` 的行重组与三层回执断言。
# v0.6 更新说明（2026-07-29）

本次按《模块统一接入与交付规范》完成从“可演示工程”到“可独立接入联调包”的补齐：新增标准平台请求信封适配层、`manifest.json`、输入/输出合约、可运行样例、最小回归测试和独立 HTTP 启动入口。标准适配层只接受流程执行引擎的 `task.dispatch`，拒绝 L4 或其他 L2 引擎直连；所有写操作强制 `idempotency_key`，并把租户、真人、项目、会话、文件、对象和工作流关联字段写入业务上下文。

`data.search` 的终态主结果统一为 `business_result`，证据和原始受控复核分别为 `evidence`、`raw_access`，不再将原始字段样本当作业务答案。未恢复 `data.aggregate`：筛选、分组、计数、求和由 `data.search` 的确定性结果承载；比例、趋势、诊断、预测仍由规则计算或分析预测引擎处理。
