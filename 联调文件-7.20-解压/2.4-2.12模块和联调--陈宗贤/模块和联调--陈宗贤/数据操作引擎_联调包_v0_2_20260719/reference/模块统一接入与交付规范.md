# 模块统一接入与交付规范

> 适用项目：汉和 AI 平台联调项目  
> 项目目录：`C:\Users\21964\Documents\联调`  
> 使用目的：其他模块修改完成后，按本文档打包交付；平台侧可以直接复制到对应目录、启动、验证、查看调用审计。

## 一、为什么要统一

本项目由前端工作台、L4 应用网关、L2 业务引擎、L1 基础模块、统一数据库和对象存储组成。

如果每个模块各自定义接口、返回字段、错误码和打包目录，后续会出现：

- 前端不知道该读哪个字段；
- 流程执行模块无法统一编排；
- 调用审计无法串起完整 Trace；
- 模块复制进项目后需要反复手工改代码；
- 数据归属标签丢失，无法判断数据属于哪个账户、Project、对话或文件。

因此所有模块必须遵守统一的“请求信封、响应格式、能力命名、数据引用、交付包结构和验收方式”。

## 二、总调用原则

平台标准链路如下：

```text
前端工作台
-> L4 应用网关
-> L2 业务引擎网关
-> L2 业务模块
-> L1 基础层网关
-> L1 基础模块
-> 统一数据库 / 对象存储
```

模块必须遵守：

- 前端不直接调用 L2/L1 模块；
- 前端不直接读写 SQLite 数据库；
- L2 模块之间不随意互相直连，应通过 L2 引擎网关或流程执行模块编排；
- L2 访问数据、权限、知识库、账号等基础能力时，必须通过 L1 基础层网关；
- 所有跨模块调用必须携带 `trace_id`；
- 所有业务数据必须携带归属标签：账户、Project、对话、文件。

## 三、统一请求信封

所有模块的业务入口必须接收平台标准请求信封。

示例：

```json
{
  "protocol_version": "1.0",
  "message_id": "uuid-message",
  "request_id": "uuid-request",
  "trace_id": "trace-xxxx",
  "parent_request_id": null,
  "source": {
    "layer": "business_engine",
    "module": "workflow-execution"
  },
  "target": {
    "layer": "business_engine",
    "module": "document-table-parsing",
    "capability": "document.table.extract"
  },
  "actor": {
    "tenant_id": "web-workbench",
    "user_id": "account-xxx",
    "authenticated": true
  },
  "context": {
    "account_id": "account-xxx",
    "project_id": "project-xxx",
    "conversation_id": "conversation-xxx",
    "file_id": "file-xxx",
    "locale": "zh-CN"
  },
  "request_type": "execute",
  "action": "document.table.extract",
  "payload": {},
  "expected_response": {
    "mode": "sync"
  },
  "idempotency_key": "optional-stable-key"
}
```

### 字段含义

| 字段 | 含义 | 是否必填 |
|---|---|---|
| `protocol_version` | 平台接口协议版本，当前使用 `1.0`。 | 是 |
| `message_id` | 本次网络消息 ID，每次请求唯一。 | 是 |
| `request_id` | 本次请求 ID，下游响应必须原样回传。 | 是 |
| `trace_id` | 端到端链路追踪 ID，同一次业务操作全链路保持一致。 | 是 |
| `parent_request_id` | 子调用指向父请求 ID。没有父请求时为 `null`。 | 否 |
| `source.layer` | 调用方所属层。 | 是 |
| `source.module` | 调用方模块名。 | 是 |
| `target.layer` | 目标模块所属层。 | 是 |
| `target.module` | 目标模块名。 | 是 |
| `target.capability` | 本次调用的能力编码。 | 是 |
| `actor.tenant_id` | 租户 ID。当前前端默认为 `web-workbench`。 | 是 |
| `actor.user_id` | 当前真实用户账号 ID。 | 是 |
| `actor.authenticated` | 是否已认证。 | 是 |
| `context.project_id` | 当前 Project ID。 | 涉及项目数据时必填 |
| `context.conversation_id` | 当前对话 ID。 | 涉及对话数据时必填 |
| `context.file_id` | 当前文件 ID。 | 涉及单文件处理时必填 |
| `payload` | 模块真正处理的业务输入。 | 是 |
| `expected_response.mode` | `sync` 或 `async`。 | 是 |
| `idempotency_key` | 写操作、创建任务、确认动作建议必填。 | 有副作用时必填 |

## 四、统一响应格式

所有模块响应必须是结构化 JSON，不允许只返回一段自然语言。

成功响应：

```json
{
  "status": "success",
  "trace_id": "trace-xxxx",
  "request_id": "uuid-request",
  "task_id": "optional-task-id",
  "data": {},
  "error": null
}
```

异步受理响应：

```json
{
  "status": "accepted",
  "trace_id": "trace-xxxx",
  "request_id": "uuid-request",
  "task_id": "task-xxxx",
  "progress": 0,
  "status_url": "http://127.0.0.1:8100/api/v1/tasks/task-xxxx",
  "error": null
}
```

失败响应：

```json
{
  "status": "failed",
  "trace_id": "trace-xxxx",
  "request_id": "uuid-request",
  "data": null,
  "error": {
    "code": "DOCUMENT_PARSE_FAILED",
    "message": "文档解析失败",
    "details": {},
    "retryable": false
  }
}
```

### 响应要求

- 必须原样返回 `trace_id`；
- 必须原样返回 `request_id`；
- 成功结果放在 `data`；
- 错误必须放在 `error.code`，不能只写自然语言；
- `message` 给人看，`code` 给系统判断；
- 需要重试时必须明确 `retryable: true`；
- 不允许在响应里返回密钥、Token、密码、完整敏感正文。

## 七、文件传递规范

模块之间不应直接传本地文件路径作为核心依据，应优先传文件引用。

推荐：

```json
{
  "uploaded_documents": [
    {
      "file_id": "file-xxx",
      "object_id": "object-xxx",
      "original_name": "采购验收.xlsx",
      "content_type": "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet",
      "size_bytes": 11820,
      "sha256": "..."
    }
  ]
}
```

允许本地联调临时携带：

```json
{
  "saved_path": "framework/data/foundation_data/objects/uploads/..."
}
```

但注意：`saved_path` 只适合本机联调，不应作为长期模块接口依赖。以后迁移到 MinIO/S3 时，应使用 `object_id` 或对象存储引用。


## 十一、模块开发边界

模块不能做的事：

- 不直接读取其他模块数据库；
- 不直接修改 `platform_data.db`；
- 不绕过 L1 数据模块写数据；
- 不绕过权限模块读取敏感数据；
- 不把用户密码、Token、密钥写入日志；
- 不用大模型做确定性金额计算；
- 不返回无法解析的自然语言错误；
- 不擅自改变能力编码；
- 不把前端页面直接绑死到某个模块端口。

模块应该做的事：

- 接收标准请求信封；
- 返回标准响应结构；
- 保留 `trace_id`；
- 写入数据时带全归属标签；
- 失败时给出明确错误码；
- 在 README 中说明输入、输出、依赖、启动方式；
- 提供最小测试样例。

## 十二、错误码规范

错误码使用大写英文和下划线。

常见错误码：

| 错误码 | 含义 |
|---|---|
| `INVALID_REQUEST` | 请求格式错误。 |
| `AUTHENTICATION_REQUIRED` | 未登录或身份缺失。 |
| `PERMISSION_DENIED` | 权限拒绝。 |
| `CAPABILITY_NOT_FOUND` | 能力未登记或不存在。 |
| `DEPENDENCY_UNAVAILABLE` | 下游依赖不可用。 |
| `DOCUMENT_PARSE_FAILED` | 文档解析失败。 |
| `DATASET_NOT_REGISTERED` | 数据集未登记。 |
| `DATA_SCOPE_MISMATCH` | 数据归属范围不匹配。 |
| `WORKFLOW_EXECUTION_FAILED` | 流程执行失败。 |
| `MODEL_GATEWAY_FAILED` | 大模型调用失败。 |
| `EXTERNAL_SYSTEM_UNAVAILABLE` | 外部系统不可用。 |
| `HUMAN_CONFIRMATION_REQUIRED` | 需要人工确认。 |
| `RECORD_VERSION_CONFLICT` | 数据版本冲突。 |

失败响应中必须包含：

```json
{
  "error": {
    "code": "DOCUMENT_PARSE_FAILED",
    "message": "文档解析失败",
    "details": {
      "file_id": "file-xxx"
    },
    "retryable": false
  }
}
```

## 十三、调用审计要求

每个模块调用都应该能在调用审计页面看到：

```text
http://localhost:5173/platform.html
```

或后端直连：

```text
http://127.0.0.1:8100/monitor
```

审计里至少应能看到：

- Trace ID；
- 调用方模块；
- 被调用模块；
- 能力编码；
- 请求输入；
- 响应输出；
- HTTP 状态；
- 业务状态；
- 耗时；
- 错误码；
- 账户、Project、对话、文件归属标签。

## 十四、验收步骤

模块交付后，按以下顺序验收。

### 1. 静态检查

检查交付包是否包含：

- `README.md`
- `manifest.json`
- `service.py`
- `contracts/`
- `samples/`
- `tests/`

### 2. 启动检查

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\framework\status_all.ps1
```

需要重启时：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\framework\stop_all.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\framework\start_all.ps1
```

### 3. 模块验证页

打开：

```text
http://localhost:5173/platform.html
```

或：

```text
http://127.0.0.1:8100/modules
```

检查该模块：

- 是否能被发现；
- 能力是否登记；
- 请求是否符合标准信封；
- 响应是否符合标准响应；
- 错误是否有结构化错误码。

### 4. 前端业务链路验证

以采购验收为例：

1. 创建账户；
2. 创建 Project；
3. 创建对话；
4. 上传采购验收文件；
5. 发送业务请求；
6. 查看意图确认卡；
7. 如有偏差，点击 `调整意图`；
8. 确认执行；
9. 查看最终用户结果；
10. 刷新页面，确认待确认卡和执行结果状态一致。

### 5. 调用审计验证

复制前端显示的 `trace_id`，到调用审计页面查询。

确认：

- 全链路使用同一个 `trace_id`；
- 每一步都有输入输出；
- 每一步都有耗时；
- 数据写入经过 L2 数据操作和 L1 数据模块；
- 账户、Project、对话、文件标签一致；
- 敏感字段没有明文泄露。

### 6. 数据库验证

当前统一数据库位置：

```text
framework/data/foundation_data/platform_data.db
```

当前上传对象位置：

```text
framework/data/foundation_data/objects/uploads/
```

业务上优先通过平台页面和接口查看，不建议人工直接改数据库。

## 十五、采购验收模块交付重点

如果下一阶段做“采购验收文件核对与摘要生成”，模块应重点满足：

### 文档解析输出

文档表格解析模块应输出：

- 文件名；
- 工作表；
- 行号；
- 合同编号；
- 采购金额；
- 发票编号；
- 发票抬头；
- 发票金额；
- 验收状态；
- 附件名称；
- 附件上传状态；
- 字段证据。

### 规则计算输出

规则模块应输出逐条规则结果：

- 规则 ID；
- 规则名称；
- 是否通过；
- 问题等级；
- 问题说明；
- 涉及合同；
- 涉及发票；
- 期望值；
- 实际值；
- 差异金额；
- 证据引用。

### 用户结果输出

内容产出模块最终返回给用户：

- 采购验收摘要；
- 采购总金额；
- 合同数量；
- 发票数量；
- 已验收数量；
- 未完成验收数量；
- 需要人工核对的事项；
- 风险点；
- 建议下一步。

用户结果不应出现：

- JSON；
- 模块名；
- 端口号；
- 内部任务 ID；
- “链路已完成”这类空泛提示；
- 未经证据支持的业务结论。

## 十九、最终原则

以后任何模块交付，都按一句话判断是否合格：

```text
复制进对应模块目录后，启动服务，模块验证页能跑通，调用审计能看到完整输入输出，前端业务链路不用为它单独改接口。
```

如果做不到，就不是标准交付包，还需要继续补接口适配。
