# 接口契约 v0.1 审核结论

审核范围：统一信封、权限动作、异步状态机、三层准入规则。

## 1. 统一信封

结论：通过，补充后可进入模块对照阶段。

统一信封覆盖架构要求的六项跨层信息：

| 架构要求 | 契约字段 |
|---|---|
| 谁在调用 | `actor`，智能体代理另放 `delegation` |
| 请求哪项服务 | `target.capability` 与 `action` |
| 请求类型 | `request_type` |
| 传入内容 | `payload` 与各类 `ResourceRef` |
| 期望返回 | `expected_response.mode/schema_ref` |
| 追踪编号 | `trace_id` |

冻结前必须确认：标识符是否全部使用 UUID；租户是否统一称为 `tenant_id`；Project 是否统一使用 `project_id`。

## 2. 权限动作

结论：动作集合足以覆盖第一条闭环。

判权触点固定如下：

1. 进入平台：`platform.enter`。
2. 调用引擎或基础能力：`capability.invoke`。
3. 读取文件、数据或资产：`file.read`、`data.read`、`asset.use`。
4. 写入、创建、修改、删除或发布：对应细分动作。
5. 调用大模型：`model.invoke`，同时执行敏感数据策略。
6. 真人确认：`human.confirm`，必须核对指定确认人、内容版本和有效期。
7. 外部系统读写：`external.read/write`。
8. 长任务最终输出、关键副作用执行前：重新判权。

权限模块只返回 `allow/deny + reason_code + obligations`，不负责流程编排，也不直接执行脱敏。

## 3. 异步状态机

结论：通过，采用七状态模型：

```text
accepted / running / waiting_dependency / waiting_human /
succeeded / failed / cancelled
```

- `waiting_dependency` 与 `waiting_human` 必须区分。
- 回调按 `event_id` 幂等，按 `sequence` 防止乱序覆盖。
- `succeeded`、`failed`、`cancelled` 为不可逆终态。
- 回调失败不能丢失任务结果，调用方仍可用状态接口查询。
- 恢复流程必须校验 `resume_token`、原始 `trace_id` 和当前状态。

## 4. 三层准入矩阵

| 接收接口 | 允许的业务来源 | 允许的返回/回调来源 | 禁止来源 |
|---|---|---|---|
| 业务应用层接口 | 前端、业务引擎层结果/通知 | 已登记业务引擎 | 基础模块直接调用 |
| 业务引擎层接口 | 业务应用层、本层对内通道 | 已登记业务引擎、基础模块层回复 | 前端直达具体引擎、基础模块主动发业务请求 |
| 基础模块层接口 | 业务引擎层、本层对内通道 | 已登记基础模块 | 前端、业务应用层、具体业务引擎绕过层接口 |

基础模块层对内通道调用权限判定服务属于唯一机制性直达。该直达只允许 `permissions.check`，不得借此调用其他业务能力。

## 5. 冻结门槛

公共契约冻结为 v1 前必须完成：

- 用一个完整示例验证同步、异步、真人确认和拒绝四条路径。
- 用现有意图分析、流程执行、规则计算和权限交付包做字段映射。
- 明确服务身份认证与回调签名方案。
- 用 OpenAPI 校验器完成语法和引用校验。
- 为所有写操作定义幂等行为。
- 为所有状态变化定义审计事件。

当前结论：可以进入“现有模块接口对照与适配表”阶段，但暂不冻结为 v1。
